# 文件选择器评估：系统原生对话框与内置自定义对话框

- 评估对象：Luban Notepad v0.3.0（commit `115c124`），Rust + GPUI，Windows / macOS / Linux 三平台。
- 对比方案：
  - **原生**：GPUI `0.3.9`（`gpui-pre`）暴露的 `prompt_for_paths` / `prompt_for_new_path`，由各平台后端实现。
  - **自定义**：项目当前的 `FileDialogState` + `render_file_dialog` 内置对话框。
- 证据来源：当前仓库代码、`gpui-kit 0.8.0` / `gpui-pre 0.3.9` 源码、Notepad++ 本地方案作参照。Windows/macOS 行为来自后端源码，未在本机实机运行；Linux 行为来自后端源码与项目现有实现。
- 结论先行：**现阶段建议保留自定义对话框作为主方案，补齐“多选、文件类型过滤、键盘/可访问性、异步目录列举”四项；不建议为了多选而整体切换到原生。** 如果产品目标变成“尽可能少的自有代码 + 最大程度贴近系统习惯 + 可访问性优先”，则改为原生优先，并接受过滤器、打开初始目录、主题/语言一致性方面的损失。详细条件见第 6 节。

## 1. 两类方案到底是什么

### 1.1 原生方案（本项目可用的形态）

GPUI 已经提供跨平台文件对话框 API：

| API | 用途 | 签名/能力 |
| --- | --- | --- |
| `prompt_for_paths` | 打开文件 / 选择文件夹 | `PathPromptOptions { files, directories, multiple, prompt }`，返回 `Result<Option<Vec<PathBuf>>>`（`gpui-pre-0.3.9/src/app.rs:1891`、`src/platform.rs:2802`） |
| `prompt_for_new_path` | 另存为 | 传入初始目录和建议文件名，返回 `Result<Option<PathBuf>>`（`gpui-pre-0.3.9/src/app.rs:1904`） |

平台后端：

| 平台 | 实现 | 关键行为 |
| --- | --- | --- |
| Windows | `IFileOpenDialog` / `IFileSaveDialog`（COM） | 多选、文件夹选择、系统“快速访问/最近位置”；打开对话框没有设置文件类型过滤器（`gpui-pre-windows-0.3.9/src/platform.rs:1531` 起，未调用 `SetFileTypes`）；保存对话框只硬编码 `All files (*.*)`（`:1612`） |
| macOS | `NSOpenPanel` / `NSSavePanel` | 多选、文件/文件夹选择、可创建目录、系统边栏/搜索/标签/iCloud；未设置内容类型过滤器（`gpui-pre-macos-0.3.9/src/platform.rs:898`、`:946`） |
| Linux | XDG Desktop Portal `org.freedesktop.portal.FileChooser`（ashpd） | 多选、文件/文件夹二选一、异步；依赖 `xdg-desktop-portal`，缺失时返回错误；不支持文件与目录混合选择（`gpui-pre-linux-0.3.9/src/linux/platform.rs:765`、`:825`、`:799`、`:888`） |

### 1.2 自定义方案（当前实现）

- 状态与标签：`crates/luban-app/src/dialogs.rs:25`（`FileDialogState`，`selected: Option<PathBuf>` 表示单选）。
- 打开入口与默认目录：`crates/luban-app/src/app.rs:1256`（工作区根目录 → 当前文件父目录 → 用户主目录 → 当前目录）。
- 目录列举：`app.rs:1318`、`app.rs:1350` 调用 `luban_core::workspace::list_directory`；该函数同步读取、目录优先、名称排序（`crates/luban-core/src/workspace.rs:24`）。
- 确认逻辑：`app.rs:1393`（打开时若目标是目录则进入，若是文件则打开；另存为走 `SaveAsRequest` 和覆盖确认；文件夹用途写回工作区/搜索目录）。
- 渲染：`app.rs:4390`，固定 820×620 覆盖层，列表行是 `div` + `on_click`，回车由订阅触发（`app.rs:280`），Esc 取消（`app.rs:2732`）。
- 覆盖确认：`app.rs:4318`（应用自己弹确认框）。

## 2. 当前自定义对话框的能力边界

| 能力 | 现状 | 依据 |
| --- | --- | --- |
| 打开单个文件 | 支持 | `app.rs:1393` 的 `FileDialogMode::Open` 分支 |
| 一次打开多个文件 | **不支持** | `selected` 是 `Option<PathBuf>`（`dialogs.rs:30`）；`FEATURES.md:20` 明确记录 |
| 文件类型过滤器 | **不支持** | 渲染中没有过滤器控件；`FEATURES.md:9` 的说明也只提到路径输入和回车确认 |
| 直接输入路径/文件名 | 支持 | 路径输入框 `app.rs:4529`，文件名输入框 `app.rs:4569` |
| 打开时的默认目录 | 支持（工作区/当前文件目录） | `app.rs:1257` |
| 选择文件夹 | 支持 | `FileDialogMode::Folder`，`app.rs:1461` |
| 另存为 + 覆盖确认 | 支持 | `app.rs:1429`、`app.rs:4318` |
| 隐藏文件跟随设置 | 支持 | `app.rs:1318` 传入 `settings.show_hidden_files` |
| 主题/应用语言一致 | 支持 | 渲染使用 `cx.theme()`，文案使用 `tr()`（`dialogs.rs:51`） |
| 键盘列表导航/多选快捷键 | **不支持** | 列表行是可点击 `div`，没有焦点/选择语义；仅输入框回车与全局 Esc |
| 搜索、最近位置、收藏、新建文件夹、图标/预览 | **不支持** | 渲染只有父目录、目录/文件行、路径输入和按钮（`app.rs:4390`） |
| 异步列举/大目录保护 | **不支持** | 列举在 UI 线程同步执行；每次渲染还会 `entries.clone()` 并重建行（`app.rs:4398`） |

自定义方案的实现量约为 600–700 行（`dialogs.rs` 的状态/文案 + `app.rs` 的入口、导航、确认、覆盖确认、渲染），完全由项目维护。

## 3. 原生方案的能力边界

### 3.1 原生明确占优的能力

- **多选打开**：三个平台后端都支持 `multiple`；Windows 用 `FOS_ALLOWMULTISELECT`，macOS 用 `setAllowsMultipleSelection`，Linux 用 `multiple(true)`。这正好补上当前 `FEATURES.md:20` 记录的能力缺口。
- **系统级位置与检索**：快速访问/最近位置、收藏、边栏、搜索、标签、云盘入口、新建文件夹、预览/图标等，由系统或桌面环境提供。
- **可访问性与键盘习惯**：原生对话框继承系统屏幕阅读器、焦点顺序、标准快捷键和输入法行为。
- **覆盖确认与保存语义**：Windows `IFileSaveDialog`、macOS `NSSavePanel` 默认处理覆盖确认；应用不必自己维护覆盖确认 UI（Linux 由门户实现决定）。
- **模态与窗口归属**：Windows 对话框通过 HWND 绑定当前窗口；macOS 使用 `NSOpenPanel`/`NSSavePanel` 的应用级模态面板，GPUI 后端没有显式传入父窗口，因此不能断言绑定到具体窗口；Linux 通过 portal identifier 绑定父窗口（`gpui-pre-linux-0.3.9/src/linux/platform.rs:786`；macOS 见 `gpui-pre-macos-0.3.9/src/platform.rs:898`、`:946`）。
- **大目录/网络目录**：枚举发生在系统对话框或门户进程，不占用应用 UI 线程。

### 3.2 原生在本项目中的硬限制

1. **没有文件类型过滤器。** `PathPromptOptions` 只有 `files / directories / multiple / prompt` 四个字段（`gpui-pre-0.3.9/src/platform.rs:2802`）。Windows 打开对话框没有调用 `SetFileTypes`；保存对话框只设置 `All files (*.*)`（`gpui-pre-windows-0.3.9/src/platform.rs:1612`）；macOS 和 Linux 后端也没有设置内容类型/过滤器。若要做 Notepad++ 风格的“文本文件/所有文件”过滤器，当前原生 API 无法表达，必须改 GPUI、改用 `rfd` 或直接写平台代码。
2. **打开对话框没有初始目录参数。** `prompt_for_paths` 只接收 `PathPromptOptions`，Windows/macOS 后端都没有设置起始目录，Linux 的打开请求也没有 `current_folder`。应用无法像现在这样默认落在工作区根目录或当前文件所在目录；只能依赖系统/门户记忆上次位置。
3. **标题与按钮文案受限。** `prompt` 只映射为确认按钮文案（Windows `SetOkButtonLabel`、macOS `setPrompt`、Linux `accept_label`）；对话框标题由平台固定（Linux 直接使用 `Open File` / `Open Folder` / `Save File`，`gpui-pre-linux-0.3.9/src/linux/platform.rs:780`、`:849`）。无法显示“选择搜索文件夹”这类应用语义标题。
4. **Windows/Linux 不支持文件与目录混合选择。** Windows 的 `FOS_PICKFOLDERS` 在“只文件/只目录”之间切换，Linux portal 也只支持二选一；`can_select_mixed_files_and_dirs` 在 Windows/Linux 均返回 `false`（`gpui-pre-windows-0.3.9/src/platform.rs:833`、`gpui-pre-linux-0.3.9/src/linux/platform.rs:888`）。当前自定义对话框可以在打开模式下进入目录、也可以单独选择文件夹，语义更灵活。
5. **Linux 依赖 XDG Portal。** portal 缺失时 `prompt_for_paths` / `prompt_for_new_path` 返回 `FILE_PICKER_PORTAL_MISSING` 错误（`gpui-pre-linux-0.3.9/src/linux/platform.rs:799`、`:862`），GPUI 文档也明确提示“Linux 上可能无法打开文件选择器”（`gpui-pre-0.3.9/src/app.rs:1890`、`:1903` 的文档注释）。最小化窗口管理器、部分容器、未安装 portal 的环境会直接失去文件选择能力。
6. **主题与语言跟随系统，而不是跟随应用。** 原生对话框使用 OS/桌面环境的主题和语言；本应用有自己的主题和 `ui_language` 设置。应用设为深色/英文而系统是浅色/中文时，会出现明显割裂。
7. **覆盖确认的职责不可控。** 原生侧由平台负责，应用无法定制文案或与“关闭/退出前保存”的批处理流程统一；迁移时需要逐平台验证是否会出现双重确认或漏确认。

## 4. 九维度对比

### 4.1 功能完整性

| 方向 | 优点 | 缺点 |
| --- | --- | --- |
| 原生 | 多选、系统位置/搜索/收藏/新建文件夹/预览、标准保存语义 | 无过滤器、无打开初始目录、Windows/Linux 无混合选择、标题固定 |
| 自定义 | 三类用途齐全、默认目录、路径直输、过滤器和多选都可在应用内实现 | 目前单选、无过滤器、无搜索/最近/收藏/图标/预览、无键盘列表导航 |

**判断：原生赢在“系统能力”，自定义赢在“可控性”。** 本项目当前最缺的两项恰好一项归原生（多选）、一项归自定义（过滤器）。

### 4.2 跨平台一致性

| 方向 | 优点 | 缺点 |
| --- | --- | --- |
| 原生 | 每个平台都是用户熟悉的面板 | 三平台 UI/行为不同；Linux 还随桌面环境（GNOME/KDE/…）变化；同一功能在不同平台的位置和快捷键不同 |
| 自定义 | 三平台布局、交互、文案完全一致 | 与 OS 惯例不同，新用户需要适应 |

**判断：若“跨平台一致”是产品卖点，自定义更合适；若“像本地应用”更重要，原生更合适。** 项目已经采用自定义标题栏和自绘 UI（见 `docs/comet/archive/2026-10-23-custom-titlebar/brief.md`），一致性权重不低。

### 4.3 主题与语言

| 方向 | 优点 | 缺点 |
| --- | --- | --- |
| 原生 | 自动跟随系统主题/语言，零维护 | 与应用主题、应用内 `ui_language` 可能冲突；Linux 门户的语言还取决于桌面环境 |
| 自定义 | 与应用主题、应用语言、字号完全一致 | 需要自己维护亮/暗主题下的所有颜色和文案 |

**判断：自定义明显更符合当前“统一外观”的产品方向。**

### 4.4 可访问性

| 方向 | 优点 | 缺点 |
| --- | --- | --- |
| 原生 | 系统级屏幕阅读器、焦点管理、键盘导航、高对比度支持 | 受平台/门户实现差异影响 |
| 自定义 | 可完全按应用设计定制 | 当前列表行是 `div` + `on_click`，没有可聚焦控件或列表语义；只能回车确认/Esc 取消，不能用方向键选择；屏幕阅读器难以获知当前选中项 |

**判断：原生明显更好。** 但需要说明：这是整个 GPUI 自绘 UI 的共性问题，不只是文件对话框；若要达到可访问性合规，单独替换对话框只能解决一小部分。

### 4.5 性能

| 方向 | 优点 | 缺点 |
| --- | --- | --- |
| 原生 | 枚举在系统对话框/门户进程，应用 UI 不阻塞；大目录和网络目录更稳 | 进程间/异步开销略高，但通常可忽略 |
| 自定义 | 无跨进程开销，行为可预测 | `list_directory` 在 UI 线程同步执行（`app.rs:1318`、`:1350`）；每次渲染 `entries.clone()` 并重建所有行（`app.rs:4398`）；超大目录、慢速网络盘、断开的 SMB 挂载可能造成明显卡顿 |

**判断：原生更稳。** 自定义侧可以改为后台列举 + 结果缓存/分页，成本中等，但需要新增状态与取消逻辑。

### 4.6 可测试性

| 方向 | 优点 | 缺点 |
| --- | --- | --- |
| 原生 | GPUI 测试平台提供 `did_prompt_for_paths` 和模拟返回（`gpui-pre-0.3.9/src/app/test_context.rs:409`），可以测调用接线 | 真实系统面板无法在无头 CI 中自动操作；三平台行为需要人工矩阵验证；portal 缺失场景要单独模拟 |
| 自定义 | 状态与确认逻辑都在进程内，可直接单元测试；UI 可在 GPUI 测试环境驱动 | 当前只有标签文案测试（`dialogs.rs:142`），导航/确认/覆盖流程没有自动化覆盖 |

**判断：自定义的“逻辑可测性”更好；原生的“真实 UI 可测性”更差。** 但两者当前都没有完整的端到端测试。

### 4.7 维护成本

| 方向 | 优点 | 缺点 |
| --- | --- | --- |
| 原生 | 平台代码由 GPUI 上游维护；应用侧只需接线，估算 120–200 行（含多选、保存、文件夹、错误处理） | 受 GPUI API 能力限制；升级 `gpui-pre` 需回归三平台；若要过滤器仍需自己补平台代码；若保留自定义回退则维护两套 |
| 自定义 | 完整可控，需求变化不依赖上游 | 约 600–700 行自有代码；每增加多选、过滤器、键盘导航、异步列举都要继续投入；边界情况（UNC、长路径、符号链接、权限错误）要自己处理 |

**判断：短期原生更省代码；长期若要“多选 + 过滤器 + 一致性”，自定义的总成本更可控。**

### 4.8 沙箱与安全

| 方向 | 优点 | 缺点 |
| --- | --- | --- |
| 原生 | Linux portal 是 Flatpak/Snap 等沙箱的官方文件访问通道；macOS App Sandbox 下 `NSOpenPanel` 提供用户授权与安全作用域 URL；Windows 对话框同样遵循系统权限 | 依赖 portal 服务；无 portal 时不可用 |
| 自定义 | 直接调用 `std::fs`，当前 tar.gz/zip/安装器分发方式下工作良好，行为透明 | 在沙箱中无法凭对话框获得额外文件访问权限；将来做 Flatpak/App Store 版时需要改用 portal 或申请宽泛文件系统权限 |

**判断：当前发布形态（Linux tar.gz、macOS zip、Windows 便携 zip/Inno Setup，见 `scripts/package-linux.sh:66`、`scripts/package-macos.sh:36`、`scripts/package-windows.ps1`）没有沙箱约束，自定义可用；一旦要做沙箱分发，原生 portal 更稳妥。**

### 4.9 迁移成本

若把三类用途全部切到原生：

| 工作项 | 影响 | 风险 |
| --- | --- | --- |
| 用 `prompt_for_paths` 替换打开/文件夹入口 | `app.rs:1256`、`:1279`、`:1296` 改为异步 receiver | 需要处理错误、取消、父窗口绑定 |
| 多选结果接入 `open_path` | 当前 `open_path` 单文件（`app.rs:492`），需要循环、去重、汇总错误、更新状态栏 | 多个大文件/失败文件的提示要设计 |
| 用 `prompt_for_new_path` 替换另存为 | 保留 `SaveThen`（关闭/退出/关闭全部）流程 | 覆盖确认可能与系统确认重复或缺失 |
| Linux portal 缺失处理 | 目前没有回退路径 | 要么保留自定义对话框作回退，要么向用户报错 |
| 删除或保留自定义实现 | 删除约 600–700 行；保留则形成双实现 | 双实现会长期增加维护和测试成本 |
| 测试 | GPUI 测试模拟 + 三平台人工矩阵 | 无头 CI 无法覆盖真实系统面板 |

**判断：迁移本身是中等规模，不是“一行 API 替换”。真正的成本在于失去过滤器、初始目录、主题/语言一致性，以及 Linux 回退策略。**

## 5. 按用途分别看

| 用途 | 原生 | 自定义 | 结论 |
| --- | --- | --- | --- |
| 打开文件 | 多选、系统位置/搜索/收藏、系统可访问性；无过滤器、无初始目录、主题/语言可能不一致 | 默认目录、路径直输、主题/语言一致、可加过滤器；当前单选、无系统位置 | 若“多选”是近期必须项且能接受无过滤器/无初始目录，原生更划算；否则自定义补多选更符合现有产品方向 |
| 另存为 | 系统保存面板、系统覆盖确认、系统位置 | 与关闭/退出前保存流程统一、覆盖确认文案可控、主题/语言一致 | 差异最小。若已决定整体切换则用原生；否则保留自定义，避免为单一用途引入两套实现 |
| 选择文件夹 | 原生文件夹面板，系统位置/新建文件夹 | 当前实现已满足工作区根目录和查找目录两个场景 | 差异最小，不建议单独切换 |

**不要按用途混用两套方案。** 同一个应用里“打开文件用原生、另存为用自定义”会造成明显的交互与视觉割裂，也会让测试矩阵翻倍。要做就三类一起做，或者三类都保留自定义。

## 6. 推荐方案

### 6.1 默认建议：保留自定义，补齐四项能力

**推荐理由：**

1. 当前三类用途都已实现且可用，切换原生并不会减少“打开/保存/选文件夹”的基本功能，只会替换外观与系统集成。
2. 原生 API 恰好缺少本项目最需要的两项可控能力：**文件类型过滤器**和**打开初始目录**；而这两项在自定义侧都能在现有架构内实现。
3. 应用已经有统一的主题、语言和自绘标题栏；原生对话框会引入主题/语言割裂，削弱现有产品一致性。
4. 当前没有沙箱分发；Linux portal 缺失的环境还需要回退方案，整体切换后很可能仍要保留自定义实现，形成双维护。
5. 自定义侧的四项缺口都有明确、局部的实现路径，不需要改动核心编辑流程。

**建议优先级：**

| 优先级 | 能力 | 预估改动 | 说明 |
| --- | --- | --- | --- |
| P1 | 多选打开 | 中 | `selected: Option<PathBuf>` 改为集合 + 行选中状态；确认时返回 `Vec<PathBuf>`；调用方循环 `open_path`、去重、汇总失败。直接关闭 `FEATURES.md:20` 的缺口。 |
| P1 | 文件类型过滤器 | 中 | 在渲染层加过滤器下拉框；用扩展名/通配符匹配过滤列表；保存时默认扩展名。原生 API 做不到这一点。 |
| P2 | 键盘与可访问性 | 中 | 列表行改为可聚焦元素，支持方向键/Home/End/Enter，维护 `active` 索引；为列表和选中项补充语义与焦点顺序。完整无障碍仍需全应用投入。 |
| P2 | 异步列举/缓存 | 中 | 将 `list_directory` 移到后台任务，带 generation/取消；渲染使用缓存结果，避免每次 clone 全量。解决大目录/网络盘卡顿。 |

**不建议现在做的：** 搜索、最近位置、收藏、图标/预览、云盘集成。这些是原生方案的主要优势，但实现成本远高于前四项，且不影响核心编辑工作流。

### 6.2 什么情况下应改用原生

满足以下任一条件时，建议整体切换到原生（三类用途一起切）：

- “多选打开”是近期必须交付的能力，且团队希望用最少的自有代码完成，而不是在自定义对话框里实现。
- 产品明确要求贴近各平台原生体验，或需要系统级可访问性/输入法/高对比度支持。
- 计划提供 Flatpak/Snap 或 Mac App Store 等沙箱分发，需要 portal / 安全作用域 URL。
- 团队更愿意把平台差异交给 GPUI 上游维护，接受“无过滤器、无初始目录、主题/语言跟随系统”的限制。

**切换时必须接受的损失：**

- 文件类型过滤器需要另找方案（改 GPUI、引入 `rfd`、或写平台代码），否则 Notepad++ 风格的过滤器会缺失。
- 打开对话框无法默认落在工作区/当前文件目录。
- 对话框标题无法表达“选择搜索文件夹”等应用语义。
- Linux 无 portal 环境需要回退或明确报错。
- 主题/语言可能与主界面不一致。

### 6.3 决策规则（速查）

```text
需要多选，且能接受无过滤器/无初始目录/系统主题语言
    → 原生（三类一起切）

需要过滤器，或强依赖应用主题/语言一致，或不希望依赖 Linux portal
    → 自定义（补多选 + 过滤器 + 键盘 + 异步列举）

多选和过滤器都必须有，且不想自己维护 UI
    → 自定义实现，或引入 rfd/平台自绘（新增依赖与平台代码，成本更高）

要做 Flatpak/Snap/App Store
    → 原生 portal 优先；保留自定义作为无 portal 回退
```

### 6.4 混合方案（原生 + 自定义回退）

技术上可行：优先调用原生，Linux 返回 `FILE_PICKER_PORTAL_MISSING` 时回退到现有自定义对话框。**但不建议作为稳态方案**：

- 两套 UI 的交互、主题、语言、覆盖确认行为不一致。
- 测试矩阵翻倍；用户在不同机器上看到不同对话框，支持成本上升。
- 只有在“沙箱分发是主路径、同时必须覆盖无 portal 环境”时才值得采用；此时应把回退限制为错误恢复，而不是常规路径。

## 7. 若选择切换：实施与验证要点

1. **异步接线**：`prompt_for_paths` / `prompt_for_new_path` 返回 `oneshot::Receiver`；在 `cx.spawn` 中等待，处理 `Ok(Some(paths))`、`Ok(None)`（取消）、`Err`（Linux portal 缺失等）。
2. **多选接入**：`open_path` 保持单文件语义，调用方循环并汇总；注意去重、已打开文件的激活、大文件大小限制、失败状态提示。
3. **另存为流程**：保留 `SaveAsRequest` / `SaveThen` 状态机；逐平台验证覆盖确认，避免系统确认与应用确认重复；Linux portal 的覆盖行为需要实测。
4. **文件夹用途**：`prompt_for_paths(directories: true)` 替换 `FileDialogMode::Folder`；注意无法区分“工作区根目录”和“查找目录”的标题，只能靠调用上下文提示。
5. **Linux 回退**：决定 portal 缺失时是报错、回退自定义，还是禁用相关菜单项；三种选择的产品代价不同。
6. **清理**：若不再保留回退，删除 `FileDialogState`、路径/文件名输入、覆盖确认 UI、渲染和订阅，避免死代码；若保留回退，明确标注“仅错误恢复”。
7. **验证矩阵**：Windows（含 UNC/长路径）、macOS（含 iCloud/沙箱）、Linux（GNOME/KDE、portal 存在/缺失）、无头 CI 仅验证调用接线与错误分支。

---

## 8. 重新评估的触发条件

出现以下任一变化时，应重新评估本结论：

- **GPUI 原生 API 增强**：新增文件类型过滤器、打开初始目录、自定义标题、文件+目录混合选择。只要过滤器可用，原生的最大短板消失，切换价值显著上升。
- **沙箱分发**：开始提供 Flatpak、Snap、Mac App Store 版本。portal / 安全作用域 URL 会成为硬需求。
- **可访问性要求**：产品需要满足 WCAG/平台无障碍审核。原生的系统对话框是更省力的路径；但若只替换对话框而主界面仍不可访问，收益有限。
- **多选成为 P0**：如果用户反馈中“一次打开多个文件”优先级高于“过滤器/主题一致性”，原生的性价比会超过自定义增强。
- **自定义实现膨胀**：当自定义对话框代码接近 800–1000 行，或边界 bug（网络盘、UNC、权限、符号链接）反复出现时，维护成本可能超过切换成本。
- **Linux portal 覆盖率**：如果目标用户中 portal 缺失比例很低，原生 + 报错的方案可接受；如果比例高，必须保留回退。
- **Notepad++ 对齐审计**：若明确要求对齐 Notepad++ 的过滤器、最近目录、覆盖语义，过滤器会成为必选项，自定义或平台自绘更合适。

**当前原生 API 无法解决、需要改 GPUI / 引入第三方库 / 写平台代码的限制：** 文件类型过滤器、打开初始目录、自定义标题、Windows/Linux 文件+目录混合选择、应用主题/语言一致性、portal 缺失时的可用性。

---

## 9. 结论

- **如果只问“哪种更先进”：原生方案**。它有多选、系统位置、系统可访问性和更好的大目录/沙箱适配，代码量也更少。
- **如果问“哪种更适合当前的 Luban Notepad”：自定义方案**。项目已经围绕统一主题、统一语言和自绘 UI 建立产品识别；原生 API 又恰好缺少过滤器和打开初始目录这两个 Notepad++ 工作流中的实际能力。把自定义补齐四项缺口，比整体切换后再弥补这些损失更可控。
- **最关键的取舍是“多选”与“过滤器”**：原生免费给多选，但给不了过滤器；自定义两者都要自己做，但都能做，且能保持现有体验。若两者只能选一个方向，先确认产品更在意哪一个，再决定是否切换。
- **不建议**为了单一用途混用两套方案；也不建议在没有 portal 回退策略的情况下直接切到原生。
